### Board and moves

- `rows` and `cols` count **boxes**, not dots. A 3x3 board has 9 boxes and 24 edges.
- Players are `0` and `1`; an unclaimed box has owner `-1`.
- Moves are integer edge IDs. Horizontal edges come first, row by row; vertical edges
  follow, row by row. Use `h_edge`, `v_edge` and `edge_coords` rather than inventing a
  separate numbering scheme. Box index is `row * cols + col`.
- `state.apply(edge)` returns a **new** state. Always keep the return value.
- A scoring move can complete one or two boxes. The scorer keeps the turn in either case.
  Use `state.current_player`; do not infer the player from move count or search depth.
- `winner()` returns `None` for both unfinished games and finished draws. Check `is_over()`.
- `apply()` rejects drawn/out-of-range edges with `IllegalMoveError`. Geometry helpers and
  `boxes_completed_by()` assume valid indices; the latter does not validate legality.
- The supported app range is 1x1 through 7x7, including rectangular/narrow boards.

For a 1x2 board the horizontal IDs are top `(0, 1)` and bottom `(2, 3)`; vertical IDs
are left `4`, middle `5`, right `6`. Replaying `[0, 2, 4, 1, 3]` leaves Player 1 to
move. Edge `5` captures the left box, then the same player takes edge `6` and the right
box. Playing `6` first gives both boxes to Player 0. The fixture and tests cover this.

### Bot calls and score meanings

```python
from dnb.bots import make_bot
from dnb.engine import GameState

state = GameState.new(3, 3)
bot = make_bot("minimax:depth=4")
scores = bot.evaluate_moves(state)  # dict[int, float], every legal move
result = bot.choose_move(state)  # MoveResult(move, score, info)
state = state.apply(result.move)
```

All scores are in `[-1, 1]` and favour the player who was about to move in the input
state. `evaluate_moves()` is deterministic for these classic bots and does not mutate
the position. It returns `{}` on a finished game; do not call `choose_move()` then.
There is no legal move to return, so that call raises `ValueError`. RandomBot retains
its existing empty-sequence error behaviour. `info` currently remains an empty dict.

Scores share a range and direction, but their numerical meanings differ:

| Bot | Score meaning | Selection behaviour |
|---|---|---|
| Random | Always `0.0` | Uniform random legal edge |
| Greedy | Local tactical preference | Capture, otherwise avoid third sides; random among equally good moves |
| Minimax | `(my boxes - their boxes) / total boxes` at the searched leaf | Highest search value; ties prefer captures, then safe edges, then lower edge ID |

Greedy gives one/two captures `0.5`/`1.0`, safe moves `0`, and moves creating one/two
three-sided boxes `-0.5`/`-1.0`. A capture is never penalised for creating a third side
next door, because it retains the turn. Its score is **not an estimated final box margin**.

### Settings

```python
make_bot("random:seed=7")
make_bot("greedy:seed=7,randomness=0.0")
make_bot("greedy:seed=7,randomness=0.3")
make_bot("minimax:depth=3")
make_bot("minimax:depth=4")
```

- Greedy `randomness` defaults to `0.0` and must be in `[0, 1]`. On each choice it is
  the probability of choosing uniformly from **all legal moves**, including mistakes.
  At `1.0` every choice is random. The returned score still describes the selected move.
- `seed` gives a reproducible random sequence for greedy/random. Evaluating greedy
  scores does not consume the sequence. Repeated choices do consume it.
- Minimax `depth` defaults to `3` and must be a positive integer. It counts **edges**,
  including the candidate edge and any extra turns. Depth 1 inspects the immediate result.
  Depth 4 means at most four edges ahead, not four alternating player turns.
- Invalid settings raise `ValueError`, which the existing game-creation endpoint already
  converts into HTTP 400. No new HTTP contract is needed.

## How minimax works

1. Remember the input state's player as the scoring perspective.
2. At every node, maximise if that player still moves; otherwise minimise. A capture can
   therefore lead from one maximising node to another maximising node.
3. Stop at the configured depth or the end of the game and compute the normalised margin.
4. Search captures before safe moves and sacrifices so alpha-beta can skip irrelevant branches.
5. Reuse exact repeated positions within the call, keyed by drawn edges, scores, current
   player and remaining depth. Pruning bounds are not stored as exact values.
6. Search each root move with a full window so every value returned to review is a valid
   depth-limited result, rather than just an upper/lower bound.

The horizon uses the box margin already scored at that leaf. Chain counting, deeper
endgame extensions and other strategic evaluation remain optional future work. Equal
shallow scores often mean the search cannot yet see a consequence; they do not prove
two moves are equally good with perfect play.

## Verification and measurements

From the repository root:

```bash
uv sync --locked --all-extras
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
uv run python -m scripts.benchmark_person1 --games 100 --output results/person1.json
```

The all-extras environment is needed because the existing explanation tests construct a
Gemini client (without making a request). No real LLM calls or API keys are used by tests.

The test suite passes **128 tests**, including the original two-random-bots checkpoint.
Minimax is compared with an independent unpruned solver on **every reachable 1x2 state**
and on seeded 2x2 positions at depths 1-4. Engine checks include 1x1, 1x7, 7x1, 2x3
and 7x7, double captures, draws, ownership, immutability and illegal edges. API tests
play complete games against both new bots with either player starting. An actual minimax
scorer also plugs into Person 4's hint and review functions.

See [the benchmark results](report/PERSON1_RESULTS.md) for measured speed and match outcomes,
and [the raw JSON](report/person1-benchmark.json) for individual game scores and timings.
Timings depend on the machine and load. This is a P1 acceptance sample; Person 2 still owns
the complete cross-bot tournament, plots and difficulty calibration.

Minimax has no time budget or automatic depth cap. High depths on large boards can be
expensive; start with low depths and profile on the demo hardware. Only a search deep
enough to finish a position solves it exactly. Full-depth 3x3/4x4 opening searches are
not recommended. Larger boards are supported for legal play, but depths 1-4 were timed
only on 3x3 and 4x4.
